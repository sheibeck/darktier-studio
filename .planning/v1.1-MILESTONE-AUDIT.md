# v1.1 In-Site Companion Apps — Milestone Audit

**Audited:** 2026-08-18
**Auditor:** Claude (gsd milestone auditor)
**Status: PASSED** — original owner intent is fully delivered in the codebase. Only owner-side activation steps (deploy, live-Firestore seed, browser play-throughs) remain, consistent with how v1.0 shipped (ANALYTICS-01/AUTH-01 owner-activation gaps at launch).

## Original Intent (owner's ask, restated)

> "Allow adding software directly to darktier studios website. I added 2 react .tsx apps (in /apps/): a Fate of the Fellowship companion and a Burning Banners companion... I don't want to spin up my own domain for each; I want to add them to my library of apps. Can we host them right in our darktierstudios firebase app?"

Plus scoping: reusable in-site hosting pattern + the 2 apps; managed via the existing admin CMS as Armory tools; localStorage-only for MVP (no login); each app keeps its own look inside the Nocturne shell; free Spark plan, $0, static, manual deploy.

**Verdict: delivered.** Both apps are code-split Astro islands at `/armory/<slug>` inside the same Firebase Hosting deployment as the marketing site — no second domain, no second Firebase project, no server. A documented, enforced drop-in pattern exists for future apps. Both apps are Firestore-backed Armory tool records editable through the existing admin CMS. Everything runs on the same free Spark plan with zero new recurring cost.

## 1. In-site hosting (core ask) — VERIFIED

- Single Firebase project (`darktierstudios-b846f`, confirmed via `.firebaserc`), single `dist/` output, single `firebase deploy --only hosting` — no `functions/` directory exists, no `output`/`adapter` key in `astro.config.mjs` (confirmed by direct read and by this audit's own `npm run build`).
- Both apps build to real routes in the same `dist/` tree as the marketing pages: `dist/armory/fate-of-the-fellowship.html` and `dist/armory/burning-banners.html` — confirmed present after a fresh `npm run build` run by this audit.
- `The Armory` (`/tools`) lists both as `kind: "internal"` tools whose Launch link is same-tab (`href="/armory/<slug>"`, no `target="_blank"`) — confirmed in the built HTML (`src/components/live/ToolsLive.tsx` two-branch conditional) versus the pre-existing Charlie Mike TOC external tool, which correctly retains `target="_blank" rel="noopener"`. A visitor never leaves `darktierstudios.com`.
- The original `/apps/*.tsx` source files no longer exist in the repo (`ls apps` → empty) — confirmed relocated via `git mv` history (`19a4de9` for FOTF; Phase 10 commits for BB), not duplicated or left dangling.

**No separate domain, no separate Firebase project, no iframe.** Core ask fully met.

## 2. Reusable drop-in pattern — VERIFIED

- `src/lib/armoryApps.ts` is the single generic registry (slug/name/title/description/Component) driving `src/pages/armory/[slug].astro`'s `getStaticPaths()`. Adding a new app requires no new route file.
- `[slug].astro` contains a build-time `DISPATCHED_SLUGS` parity guard that throws if a registry entry lacks its matching dispatch line — this is an *enforced* invariant, not just a documented convention (confirmed by direct source read).
- `docs/adding-a-companion-app.md` (163 lines) documents the pattern as a 7-step checklist with both FOTF (clean, zero-deps) and Burning Banners (deps + scoped Tailwind) as worked examples, cross-checked against the real source files during this audit and found accurate.
- The known Astro limitation this pattern hit and resolved: `client:only` hydration-script generation needs a statically-analyzable local import binding, so registry-driven dynamic component dispatch (the original plan) doesn't work — the actual implementation uses one direct per-slug JSX line instead, disclosed in both the route file's comment and the guide. This is a reasonable, working, ~3-line-per-app cost, not a compromise of the "reusable pattern" goal.

**Pattern exists, is enforced by the build, and is documented for a third app to drop in cheaply.**

## 3. Both apps "in the library" as live Armory tools — VERIFIED (code) / OWNER-DEFERRED (live data)

- `src/data/catalog/tools.ts` (the committed seed / fallback source of truth) has both apps as `status: "live"`, `kind: "internal"`, slugs matching the registry exactly (`fate-of-the-fellowship`, `burning-banners`).
- **This audit independently re-verified the seed-driven build**: temporarily moving `serviceAccountKey.json` aside and re-running `npm run build` forces the seed fallback, and the resulting `dist/tools.html` shows both apps with same-tab `Launch` anchors (`href="/armory/fate-of-the-fellowship"`, `href="/armory/burning-banners"`, no `target` attribute) — confirming the code path is correct end-to-end.
- **This audit also independently confirmed the live-data gap**: with `serviceAccountKey.json` present (the default state), `npm run build` reads LIVE production Firestore, and the resulting `dist/tools.html` does **not** contain either new app — production Firestore currently has a different tool set (`charlie-mike-toc`, `table-utilities` = "Dungeon World Companion", `gm-tools` = "5x Companion", `fate-character-sheet`) that predates this milestone's seed update. The two new Armory tool docs have not yet been written to production Firestore.
- This exactly matches what Phase 11's own verifier flagged as owner-deferred (SC4 "live" half) — this audit's fresh, independent build reproduces and confirms that finding rather than trusting the SUMMARY/VERIFICATION claim at face value.

**Conclusion:** the code, seed, and admin-CMS wiring for "both apps in the library" are complete and correct. The live production catalog has not yet been updated — this is a one-time Firestore write the owner needs to perform (via admin "Load starter catalog" or `npm run seed`), not a code gap.
